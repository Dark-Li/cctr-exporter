# PDF 方向格式符、原字体与局部内容尺寸评估

用户截图报告题目 `76142097` 在题干出现 `U+200E`，源字体为 Times New Roman，来源为行内 CSS。本轮只读源码和现有依赖 API，未读取截图文件、系统字体或真实题文，也未启动程序。

U+200E 是 LEFT-TO-RIGHT MARK，类别 Cf，双向类型 L。它不显示字形，但可影响混合方向文本中数字、括号和标点的顺序，不能当作普通缺字处理。它同时属于默认可忽略码点，这不等同于可以丢弃其排版语义。依据见 [Unicode 字符数据库](https://www.unicode.org/Public/UCD/latest/ucd/UnicodeData.txt)、[派生属性](https://www.unicode.org/Public/UCD/latest/ucd/DerivedCoreProperties.txt)和 [UAX #9 的方向标记说明](https://www.unicode.org/reports/tr9/#Directional_Formatting_Characters)。

当前 `PdfHtmlContent.kt:138–145` 仅把 ISO 控制字符排除出可见字形检查。LRM 不是 ISO 控制字符，在嵌入思源字体没有对应 glyph 时进入局部字形回退。`PdfSourceFont.kt:26–29` 只支持已验证的 Symbol／Wingdings，因此拒绝 Times New Roman。`pdfText` 的检查也有同样分类问题。截图表明的是这条分流错误，不能据此判定 Times New Roman 不支持所需可见文字。

最小修复应先把方向标记与可见字符分开。对已确认仅含从左到右的中文、英文、希腊数学文字且没有 RTL 上下文的段落，LRM 应作为零宽格式参与处理，避免要求可见 glyph 或生成图片。若必须在绘制副本省略，也只限这种已经确定的方向语境，并验证原文顺序与提取。包含阿拉伯文、希伯来文、右向数字、显式方向样式或其它双向控制时，应使用经过验证的双向排版流程。不能删除全部 Cf，连接符、换行控制和数学不可见操作符各有不同语义。现有 iText 包有非打印字符工具，但其零宽输出和双向处理仍需针对性验证，不能仅跳过一个检查就宣称完成。

对真正可见的文字，按原字体分段生成原生 PDF 文本是可行的。包内 iText 8.0.4 已有 `PdfFontFactory`、`FontProvider` 和 Unicode 编码／嵌入接口，可复用现有 DOM 字体来源解析，在每个连续文本段选择实际字库。拉丁字母和可覆盖的数学符号用源字体，中文缺字回退到已有嵌入思源字体，粗体和斜体选择真实对应字面。每个 PDF 独立管理字体实例，验证 glyph、嵌入标志和 ToUnicode，保持复制搜索。相关 API 见 [PdfFontFactory](https://api.itextpdf.com/iText/java/8.0.4/com/itextpdf/kernel/font/PdfFontFactory.html)与 [FontProvider](https://api.itextpdf.com/iText/java/8.0.4/com/itextpdf/layout/font/FontProvider.html)。复杂双向和连写支持需另核现有依赖，参考 [iText 排版说明](https://itextpdf.com/blog/technical-notes/displaying-text-different-languages-single-pdf-document)。

原字体排版仍须确认目标系统实际存在的字体、内部 family 与字面身份、允许嵌入的方式，以及文件在其它机器能否正常显示。同名字体不一定拥有同一私用区语义。Symbol 保留已经按来源核实的映射，不能只因加载原字体就把 PUA 当成标准 Unicode。原字体不可得时提供明确诊断；有可验证原字形但不能原生嵌入时，才局部保真渲染，并保留相邻原生文字。整题截图会失去正文可复制性，不适合作为默认方案。

工作量可分两步。第一步修正 LRM 的方向／非打印分类，针对当前纯 LTR 题库验证即可，范围较小。第二步扩展原字体原生输出，涉及字体解析、字面匹配、缺字回退及提取验证，范围更大。验收应覆盖 LRM 位于正文首尾、数字括号两侧、中文英文希腊混排及真实 RTL 对照，另检查 Times 普通／粗／斜、中文回退、Symbol PUA、缺失字体、上下标、表格、换页和可复制内容。本轮为评估，产品、测试和依赖均未修改。

## 第二个案例：局部内容尺寸错误

用户另提供截图：题目 `42732302`，分组为概率习题／随机变量的数字特征／填空，时间 `2026-11-16T21:51:09.605`，错误为「局部题目内容尺寸无效或过大」。仅以截图报告作为该案例证据；指定隔离诊断会话的 stdout／stderr 未找到此 ID，未取得该次堆栈、资源类型或实际宽高，没有重新触发任务或读取题文、账号、数据库。不能认定该题也包含 U+200E、PUA，或将它归入答案阶段。

当前源码 `DriverUtil.kt:96–124` 在图片 decode、字体 ready 和两次动画帧之后取得局部容器的矩形与 scroll 尺寸，向上取整并转换为整数，要求 **CSS 总宽 9–4000、总高 9–10000、宽乘高不超过 8,000,000**。任一条件不满足均产生截图中的同一句错误，因而「无效」与「过大」目前无法区分。该分支已经收到尺寸列表；图片解码／资源等待失败另报「题目图片或公式加载失败」，DPR 非有限或非正也另有错误。宽高没有转换前的显式有限值分类，现有提示不足以反推原始数值。

容器四边各有 4 CSS px 防裁留白。空、隐藏或零几何内容可能只剩 8×8，也会被最小值 9 拒绝；合法的极窄／极矮内容（不足 1 CSS px）也需要与空内容分开验证。不能据此提示就推断内容太大，也不能按透明墨迹最低点随意裁掉防裁边。反过来，过长的不可换行局部字形、极宽／极高 SVG、MathML 或图片也可能越界，但本题没有几何证据证明其中任何一种。

捕获路径可能来自两类调用：`PdfHtmlContent.kt:216–237` 为连续未支持字符重建固定 11／8.5pt 字号、`white-space:pre` 的源字体片段；`PdfHtmlContent.kt:322–326` 为复杂公式／图片提交独立元素。前者不会直接继承原祖先的大字号，但长连续片段可能过宽；后者隔离后不一定保留祖先的相对尺寸语境。普通远程图片受 650 CSS px 宽度限制，SVG 图片不受该条规则限制，纵横比仍可能形成过高内容。上述均为待验证候选，而非该题已证原因。方向标记和原字体原生排版可减少文字片段截图，但不能单独解决公式／图片的几何问题。

PDF 侧 `sizeImage`（`PdfHtmlContent.kt:361–367`）在捕获成功后才按页面或单元格可用宽度等比缩放，所以当前页面缩窄无法挽救浏览器捕获前已越界的内容。现捕获统一为每 CSS px 两个输出像素，现有面积上限已允许约 3200 万像素，单份 ARGB 像素约 128 MB，尚未计算截图、解码和重新编码副本；不宜直接放宽阈值。

## 合并后的最小实施顺序

1. 先区分零宽方向格式与可见文字，处理 LRM 的方向语义；再将真实可见文字按有效源字体／字面原生排版并有序回退中文字体，保留字体限定的 Symbol 映射。此项以可复制文本为优先，不能将所有 Cf 删除或把未知 PUA 强行映射。
2. 将局部捕获错误细分为非有限几何、空／零几何、单边超限及面积超限。仅记录题 ID、阶段、资源类别、CSS 宽高／内容框／scroll 尺寸、DPR、字符数量等纯元数据，不记录题文、答案或资源地址。先验证原始数值再取整，必要时保留小数尺寸，以免把合法细线误当空白。确定无可见语义的隐藏／方向节点不应生成截图；其它有语义却没有有效几何的内容应明确失败。
3. 对确实过大的正尺寸资源，在捕获前结合最终页面／表格可用宽度选择等比局部布局；仍超预算的长资源采用有界分块，连续文字优先原生换行，复杂公式保留整体比例及完整内容。块之间保持源覆盖连续，并正确换算原基线和留白。仅缩小截图 clip 会裁内容，应禁止。降低像素密度只能作为有明确清晰度验收的受限策略，不能代替完整性校验；仍不可安全处理时保留明确错误和旧归档，不扩展为静默跳题。

回归在上一节文字／字体用例之外，增加空节点、隐藏节点、仅方向符、合法亚像素细线、长源字体片段、相对尺寸 SVG／MathML、极宽公式、极高图片、窄表格与多页连续分块；检查边界附近的尺寸／面积、完整首尾、分数上下标、等比缩放、基线及行距、相邻正文复制、失败旧件保护。无需全局改截图尺寸上限，也不把全部格式问题转为图片。
