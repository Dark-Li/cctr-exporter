# 导出任务失败且界面无原因诊断

2026-11-24。基于任务 109–112 的文件日志、SQLite 日志表和 Exposed 列类型校验确认。

## 现象

- 任务 109 / 110 / 112 导出「26-27 材料工程基础练习」，进度到 90–100% 后状态变为 FAILED。
- 任务 111 导出「无机非金属材料工程专业 26-27-1材料科学基础 练习」，同样在接近完成时失败。
- 应用内任务日志只有 INFO 进度，没有任何失败原因。

## 已验证的原因

- 109 / 110 / 112：`质量传递原理 / 判断题` 的 4 道题（ID 43192426–43192429）题干含 `U+200F`（RLM）。`PdfTextDirection.pdfLtrText` 只跳过 `U+200E`，其余 bidi 控制符直接抛「PDF 暂不支持双向文本」。
- 该组 4 道题全部命中，触发 `writeSelectableQuestionPdf` 的「整组失败」分支；`writeQuestionPdfArchive` 在第一个失败组终止整个任务，所以 565 题在第 100% 时整体失败。
- 111：计算题 ID 42872878 的参考答案图片捕获失败，`layout-context-changed`，CSS 为 560.484375×9.0，盒子数量或尺寸在测量与校验之间变化。
- 日志表 `logger.message` 是 `varchar(200)`；Exposed `VarCharColumnType.validateValueBeforeUpdate` 会拒绝超过 200 个码点的字符串。本次失败消息长度分别为 266、266、217、266 字符，历史上成功入库的 ERROR 消息为 47–179 字符。
- `task-logger.kt` 用 `scope.launch` 异步写库且无异常处理，插入被拒后异常被静默吞掉；日志页只读 SQLite，因此界面看不到原因。
- 任务 110 和 112 在 `logger` 表中的记录数为 0（文件日志完整），说明失败插入之后同一进程的后续日志写入也失效，重启后恢复；具体为连接/事务被长消息插入卡住还是其他原因，修复后需用连续失败复测确认。

## 修复

- `Loggers.message` 改为 `text`；SQLite 现有列虽标为 VARCHAR(200) 但不限制长度，Exposed 改用 TextColumnType 后即可写入长文本，无需迁移。
- `Task.logAndSave` 在更新任务状态前等待失败原因入库；异步日志增加异常处理与文件日志回退。
- `U+200F` 与 `U+200E` 一样作为不可见方向标记丢弃；真正的 RTL 字符和 `202A–202E`、`2066–2069` 仍然拒绝。
- 整组都是内容不支持时抛 `PdfGroupSkippedException`，任务跳过该组继续出包。
- 单题的致命错误（答案解码、浏览器截图）在同组还有成功题目时仅跳过该题；整组都失败时才按原样上抛，保留既有「浏览器/答案错误不静默跳过」的契约。
- 局部截图失败自动换一次会话重试。

## 边界

- 整组失败且包含致命错误时仍然失败任务，避免 Edge 会话整体损坏时产出大面积缺失的包。
- 跳过题目会记录 ID 和原因，任务提示为「部分导出完成」。
